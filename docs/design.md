# Kekkai Design Doc — サーバーサイド特化・型で証明可能な言語

Oct 4, 2026 · @Shogo Kawamura

## 概要

Kekkai（結界）は、サーバーサイドの典型的なバグ（トランザクション不整合、隠れた副作用、認可漏れ、個人情報の漏洩、範囲外アクセス）を型検査で排除する言語である。コンパイラはWasmGCへ出力し、実行環境は当面Cloudflare Workersとする。最終的にはセルフホスティングする。

動機はLLM時代の分業である。コードはLLMが書き、正しさは型検査器が保証する。型が仕様になり、capabilityが生成コードの影響範囲を限定する。

コアは次の3本柱で構成し、依存型は入れない。

- **capability渡し**（第二級値、必要に応じて線形）
- **エフェクトの可視化**（capabilityの有無で表現）
- **篩型＋SMT**（線形整数算術に限定）

## ゴールとノンゴール

**ゴール**

- トランザクションの整合性を型で保証する（必須）
- 副作用の有無を型で保証する（必須）
- 添字アクセスでpanicしないことを保証する
- 認可チェックの通過と個人情報の非漏洩を型で表す
- Bazel的なインクリメンタル処理を言語仕様に含める
- コア計算体系の健全性をLeanで証明する

**ノンゴール**

- 完全な依存型（Lean、Idris相当の表現力）
- トランスパイラ実装自体の形式検証（差分テストで担保する）
- 認可ポリシー自体の正しさの証明
- タイミングなどのサイドチャネル対策
- SMTソルバの検証（公理扱い）
- 初期版でのWorkers以外の実行環境（wasmtimeなど）への対応

## 保証する性質

優先度P0はトランザクションと副作用。多くの性質は同じ仕組み（capability、情報フローラベル）の応用で得られる。

| 性質 | 防ぐもの | 実現方法 | 優先度 |
| --- | --- | --- | --- |
| トランザクション整合性 | commit漏れ、二重commit、tx内のロールバック不能な副作用 | 線形な `Tx` capability | P0 |
| 副作用の有無 | 隠れたI/O | capability渡しによるエフェクト | P0 |
| 添字の安全性 | 範囲外アクセス、ゼロ除算、オーバーフロー | 篩型＋SMT | P1 |
| 決定性 | 再現しないバグ | `Clock`・`Random` もcapabilityにする | P1 |
| 冪等性 | リトライでの二重実行 | `Idempotent` ハンドラは冪等な操作のみ呼べる | P1 |
| エラーの網羅 | 処理されない例外 | 例外を廃止し、エラーを型で表す | P1 |
| 認可 | チェック漏れ、権限の取り違え | `Can<Action, resource>` capability | P2 |
| 個人情報の非漏洩 | ログやレスポンスへの漏洩 | 最小版は表示不可のPii型、本格版は情報フロー型 | P1（本格版はP2） |
| テナント分離 | テナント間のデータ混入 | テナントをラベルにした情報フロー型 | P2 |
| クエリコストの上限 | N+1クエリ、無制限ページング | DB capabilityに回数・件数の上限 | P3 |
| API互換性 | 破壊的変更 | 旧バージョンとの型差分検査 | P3 |
| マイグレーション安全性 | ロック、データ欠損 | 型付きスキーマ変更、expand/contractの強制 | P3 |
| 依存ライブラリの権限 | サプライチェーン攻撃 | capability方式で自動的に成立 | — |

## 型システム設計

エフェクトは代数的エフェクト（Koka型）ではなく、capability渡し（Effekt型）を採用する。トランザクション、認可、エフェクト、並行性を「スコープから逃げないcapability」という1つの概念に集約できるためである。

```rust
#[handler]
fn delete_user(req: Request, db: &DbPool, log: &Log, _auth: Authed<Admin>) -> Response {
    let id: UserId = req.path("id").parse()?;  // 篩型で検証済み
    db.transaction(|tx| {                       // tx は線形
        tx.delete(users, id)?;
        tx.commit()                             // commit か rollback が必須
    })?;
    log.info("deleted", id);                    // PII は Log に渡せない
    Response::no_content()
}
```

表面構文はRust風とする。`&Cap` は「スコープ内でだけ借りるcapability」を表し、保存も返却もできない。エラーは `Result` と `?` で扱う。

### capability渡し

- 副作用は、対応するcapability（`DB`、`Net`、`Log`、`Clock`、`Random` など）を引数で受け取ったときだけ起こせる。capabilityを受け取らない関数は純粋である。
- capabilityは第二級値とする。引数として受け取れるだけで、返り値・変数・フィールドに保存できない。これでスコープ外への漏洩を注釈なしで防ぐ。
- 表現力が足りなくなれば、Scala 3方式のcapture checkingへ拡張する。
- Rustのライフタイムと似た発想だが、追跡対象はcapabilityのみ。メモリはGCに任せる。

### 線形なトランザクション

- `Tx` は線形（affineではない）。commitかrollbackでちょうど1回消費されなければ型エラー。
- トランザクションブロック内では `Net` や `Email` などロールバック不能なcapabilityを使えない。
- そうした副作用は `Outbox` に積み、commit後に実行させる。

### 篩型

```rust
fn get<T>(a: &[T], i: usize) -> &T
where
    i < a.len()        // 篩型の条件。呼び出し側でSMTが証明する
```

- 分岐条件やループ範囲から得た事実をSMTソルバ（Z3）が使い、自動で証明する。
- 述語は線形整数算術（QF\_LIA）に限定して決定可能性を保つ。
- 証明できない箇所は `Option` を返すAPIへ逃がす。基本はイテレータ中心で添字アクセス自体を減らす。
- 入力検証も同じ仕組みで行う（parse, don't validate）。
- 型検査器は双方向型検査で実装する。

### エラー処理

`Result` と `?` を土台にし、panicは持たない。失敗はすべて `Result` で表され、関数の失敗の可能性は戻り値の型だけで分かる。

```rust
fn load(id: UserId, db: &Db) -> Result<User, DbError | ParseError> {
    let row = db.get(users, id)?;   // DbError
    let user = User::parse(row)?;   // ParseError
    Ok(user)
}

db.transaction(|tx| {
    tx.debit(from, amount)?;        // 失敗したら自動でrollback
    tx.credit(to, amount)?;
    tx.commit()
})?;
```

- **エラー型の自動合成**：`?` を使うとエラーの和（`DbError | ParseError`）を推論する。列挙型と `From` 実装を手で書く必要がなく、match では網羅性チェックが効く（Zigの推論されるエラーセットと同じ発想）。
- **失敗箇所の自動記録**：`?` で返すたびに、コンパイラが呼び出し位置を軽量なトレースとして積む（Zigのerror return traceに相当）。手で付ける文脈メッセージは `Public` な値しか受け取らず、エラー経由の個人情報漏洩を防ぐ。
- **トランザクションとの整合**：`transaction` ブロックのクロージャは `Result` を返し、`Err` で抜けたら自動でrollbackする。`?` で早期リターンしても線形性は保たれる。
- **panicなし**：範囲外アクセスやゼロ除算は篩型で排除する。証明できない箇所は `Option` や `Result` を返すAPIを使う。
- **リトライ可能性の型**：エラーに「リトライ可能か」を型で付け、Workflowsのリトライ方針や冪等性の保証と連動させる。

## 並行性

スコープを持たないタスク生成は言語から外し、構造化並行性のみを提供する。子タスクが親スコープより長生きすると、capabilityが漏洩して線形の `Tx` も二重に使われるためである。

```
scope { s =>                       // s: Scope capability
  let a = s.spawn { fetchUser(db, id) }
  let b = s.spawn { fetchOrders(db, id) }
  (a.await, b.await)
}                                  // 全タスクの終了を保証
```

- `spawn` は `Scope` capabilityを要求する。並行処理の有無も型に現れる。
- 複製可能な capability（`DBPool` など）は複数タスクで共有できる。線形の `Tx` は1タスクにしか渡せない。
- キャンセルとデッドラインは scope 単位で伝播する（言語が強制する）。
- async/awaitは採用しない。I/Oに到達する関数だけをコンパイラがCPS変換し、Workersのイベントループ上で動かすことで、関数の色分けを避ける。
- 長寿命のバックグラウンドワーカーは、サーバー起動時の最上位 scope にだけ置ける。

## 認可と情報フロー

どちらも型で表せるが、保証できるのは「チェックを通ったこと」と「ラベルに従って流れたこと」までである。

### 認可

```
authorize : (u: User, d: Doc) -> Option<Can<Edit, d>>
  // d.owner == u.id のときだけ返す（篩型で証明）
editDoc : (d: Doc, cap: Can<Edit, d>) -> ...
```

- `Can<Edit, d>` は `authorize` 経由でしか作れない。チェックを通らずに処理へ到達する経路がなくなる。
- 型にリソース `d` を含め、別リソースの権限との取り違えを防ぐ。
- ポリシー自体の正しさは対象外。必要ならAWS CedarのようにSMTで別途検証する。

### 個人情報の最小版（P1）

個人情報を「表示できない型」にするだけで、ログ漏洩の大半を防ぐ。非干渉性の証明を待たずに先行して入れる。

```rust
let email: Pii<String> = user.email;

log.info("login: {}", email);          // 型エラー：Pii は Display を実装しない
log.info("login: {}", email.mask());   // OK："s***@example.com"
log.info("login: {}", email.hash());   // OK：突き合わせ用のハッシュ
```

- `Pii<T>` は `Display`・`Debug`・シリアライズを実装しない。外に出すには `mask()` や `hash()` などの明示的な格下げを通す。
- 塞ぐ出口：ログ、エラーメッセージとスタックトレース、メトリクスのラベル、トレースのspan属性、HTTPエラーレスポンス、`kek replay` の記録。いずれも `Public` な値しか受け取らないcapabilityを経由させる。
- 格下げの呼び出し箇所は `kek caps` で一覧化し、レビュー対象にする。
- 分岐を通じた暗黙のフローは最小版では追わない。下の本格版で扱う。

### 個人情報の本格版とテナント分離（P2）

```
email : Labeled<PII, String>
Log.info : Public<String> -> ()                 // PIIを渡すと型エラー
mask  : Labeled<PII, String> -> Public<String>  // 明示的な格下げ
```

- 目標とする定理は非干渉性（Publicな出力はPIIな入力に依存しない）。
- 分岐を通じた暗黙のフローはプログラムカウンタのラベルで追跡する。
- ラベルはスキーマ定義で付ける。付け忘れは保証の対象外。
- テナント分離も同じ仕組みで、テナントIDをラベルとして扱う。

## インクリメンタル処理

capabilityを一つも受け取らない関数は構造的にhermeticであり、サンドボックスなしでキャッシュしてよい。この性質を使い、3つの層でインクリメンタル処理を言語仕様に含める。

1. **コードのインクリメンタル化**（Unison方式）
   - 定義を内容のハッシュで識別し、型検査・コンパイル・テスト結果を定義単位でキャッシュする。
   - 純粋なテストは、依存ハッシュから影響を受けるものだけ自動選択して再実行する。
   - 現状：`kek test` はテストの定義ハッシュ（trans）をキーに結果をキャッシュし、影響を受けたテストだけをビルド・実行する（モックは決定的なので capability を受け取るテストも対象）。`kek build` はプログラム全体のハッシュで `module.wasm` をキャッシュする。定義単位のコンパイル結果のキャッシュは今後の課題（[parallel-build.md](parallel-build.md)）。
2. **ユーザー定義アクション**（Bazel方式）
   - `action buildIndex(src: Blob) -> Index` のように宣言し、入力は引数のみ、capabilityなしを型で強制する。
   - 入力ハッシュとコードハッシュで結果をキャッシュする。Bazelの宣言漏れ問題は原理的に起きない。
3. **実行時のインクリメンタル化**（Salsa / Adapton方式）
   - DBから導出されるデータを `derived` として宣言する。
   - 読み取ったデータのバージョンを依存として記録し、変化した部分だけ再計算する。

決定性（`Clock`・`Random` のcapability化）が全層の前提になる。

## ツールチェーン（kek）

ビルド、テスト、リモートキャッシュ、カバレッジ、ミューテーションテストを、単一のCLI `kek` として言語に組み込む。拡張子は `.kek`。すべて「定義のハッシュ」と「capabilityを持たなければhermetic」という2つの性質の上に作る。

| コマンド | 設計 |
| --- | --- |
| `kek build` | 依存は型検査器が import から導出し、BUILDファイルを書かない。定義単位でキャッシュし、Bazel向けにはルールを提供する |
| `kek test` | テストは通常の関数。外部依存はモックcapabilityを渡して差し替える。変更の影響を受けるテストだけを依存ハッシュから選んで実行する |
| リモートキャッシュ | BazelのRemote Execution API互換のCAS＋アクションキャッシュ。キーは「定義ハッシュ＋依存＋コンパイラバージョン」 |
| `kek cover` | 中間表現で計測を埋め込む。結果は定義単位でキャッシュする（現行：型検査前の AST に計測を埋め込み、テストごとの結果を `trans` ハッシュでキャッシュ。README 参照） |
| `kek mutate` | 型付き中間表現上で変異体を作る。変更された定義だけを対象にし、その定義をカバーするテストだけを実行する（現行：型付き AST 上の変異体をミュータントスキーマとして 1 つにビルドし、型で検出された変異体を別に数える） |

**言語に組み込む利点**

- **キャッシュの安全性を型が保証する**：capabilityを受け取らないテストやアクションだけを無条件にキャッシュする。`Clock`・`Random` もモックなら決定的なので対象にできる。flakyなテストがキャッシュされる事故が起きない。
- **型付きの変異体だけを生成する**：型エラーになる変異体を最初から作らない。篩型に違反する変異体は「型で検出」として別に数え、型システムがどれだけバグを防いでいるかの指標にする。
- **変異体の結果もキャッシュする**：「変異体のハッシュ × テストのハッシュ」をキーにすれば、変更差分だけを再実行するインクリメンタルなミューテーションテストになる。その結果から得た「どのテストがどの変異体を検出したか」でテストの間引きもできる。
- **篩型からテスト入力を生成する**：篩型の条件を満たす値をSMTで生成し、プロパティベーステストを標準で提供する。第一段階として、`#[test]` の引数の型（`Int`・`String`・`Vec`・自前の struct/enum など）から入力を生成・縮小するプロパティベーステストを実装済み（README の `kek test`）。篩型の条件を満たす生成は今後の課題。

**ベンチマーク（`kek bench`）**

- 実行時間に加え、命令数・アロケーション数・クエリ回数といった**決定的な指標**を計測する。CIでもノイズがなく、リモートキャッシュにも載せられる。
- 実行時間はマシンに依存するので、キャッシュのキーにマシンの識別子を含める。
- DBやネットワークはレイテンシモデル付きのモックcapabilityで差し替える。
- ベースラインとの比較で性能の劣化（特にN+1クエリの発生）を検出する。

**capabilityの可視化（`kek caps`）**

- 型検査済みの呼び出しグラフから、各定義がどのcapabilityに到達できるかを算出する。
- `kek caps diff` でPRごとの権限の増減を表示する（例：「`billing::charge` が新たに `Net` を使う」）。
- モジュール単位のポリシー（例：`billing` から `Net` を禁止）をCIで検査する。

**本番リクエストの再現（`kek replay`）**

- `Clock`・`Random`・I/Oはすべてcapabilityなので、その境界で入出力を記録すれば手元で決定的に再現できる。
- `Labeled<PII, T>` の値は記録時に自動で伏せる。情報フロー型がそのまま記録の安全性にも効く。
- 記録は定義ハッシュと紐づけ、どのバージョンのコードで動いたかを特定できるようにする。

**本番での未使用コード検出（`kek unused`）**

- 本番バイナリに、定義ごと・分岐ごとに1ビットの「実行された」フラグを埋め込む。一度立てば以降は書き込まないので、オーバーヘッドは小さい。
- 全インスタンスのフラグを定義ハッシュ単位で集約する。ハッシュが同じ定義はデプロイをまたいで観測を引き継ぐ。
- 静的な到達可能性、テストカバレッジ、本番での実行を突き合わせて分類する。

| 分類 | 意味 | 対応 |
| --- | --- | --- |
| 静的に到達不能 | どこからも呼ばれない | 削除 |
| テストでのみ実行 | 本番では一度も通らない | 削除候補 |
| どこでも未実行 | テストも本番も通らない | 削除かテスト追加 |
| 付与されたが未使用のcapability | 権限を持つのに使っていない | 権限を削る |

- 年次バッチや障害時の処理など、稀にしか通らない経路は `#[rare]` で除外する。観測期間は `kek unused --since 30d` のように指定する。

**類似コードの検出（`kek similar`）**

LLMが既存の実装を探さずに似た関数を書き足すのを防ぐ。コンパイラの診断として仕様に含め、CIで強制できるようにする。

| 類似の種類 | 検出方法 |
| --- | --- |
| 完全一致（変数名だけ違う） | 定義ハッシュを名前に依存しない形（α同値で正規化）で計算するので、同じハッシュになり自動で検出される |
| 定数やリテラルだけ違う | 定数を抽象化した型付き中間表現のハッシュで検出し、引数化を提案する |
| 構造が近い | 部分木の指紋（MinHashなど）で候補を絞り、木の編集距離で判定する |
| 書き方は違うが意味が同じ | 純粋関数に限り、篩型から生成した入力で出力を比較する。線形整数算術で表せる小さな関数はSMTで等価性を証明する |

- **型とcapabilityで候補を絞る**：シグネチャと受け取るcapabilityが一致する定義同士だけを比較するので、大規模なコードでも軽い。
- **書く前に防ぐ**：型から既存の定義を検索する機能（Hoogleのような型検索）をLSPとJSON出力で提供し、LLMエージェントが新しい関数を書く前に問い合わせられるようにする。
- **差分で検査する**：`kek similar --diff` で、PRで追加された定義と既存の定義の類似だけを報告する。結果は定義ハッシュ単位でキャッシュする。
- **意図的な重複**は `#[allow(similar)]` で理由とともに明示する。閾値はプロジェクトごとに設定できる。

実装の状況（`compiler/similar_main.kek`・`similar_tree.kek`、使い方は README と [tooling.md](tooling.md)）：上の表の最初の 3 つ（`duplicate`・`literals`・`structural`）、シグネチャによる絞り込み（`-all` で解除）、`#[allow(similar)]`、`kekkai.toml` の `[similar]` による閾値、`-base` と `./kek similar -diff <rev>` は実装済み。構造の比較は、リテラルの値と局所変数の番号を抽象化したラベル列の MinHash で候補を絞り、ラベル列の編集距離（木の編集距離の下界）で枝刈りしてから Zhang–Shasha の木の編集距離で判定する。コンパイラ自身（約 1500 関数）で 10 秒ほど。意味の等価性は `-semantic` で、プロパティテストの生成器を使い出力を比べる（SMT による証明は未実装）。未実装：定義ハッシュ単位の結果のキャッシュ、`expires` の期限切れの検査。

## 実装アーキテクチャ

コンパイラ `kek` はKekkai自身で書き（セルフホスティング）、出力はWasmGCモジュールとする。実行環境は当面Cloudflare Workersに割り切る。

1. **パーサ**：Rust風の表面構文をASTへ
2. **型検査**：双方向型検査。capabilityの非漏洩、線形性、情報フローを検査し、篩型の検証条件を自作の小型QF\_LIAソルバで解く
3. **中間表現**：型情報を消去した小さな言語。Leanの参照インタプリタはこの意味論を実装し、差分テストの基準になる
4. **WasmGCコード生成**：自前のGCは持たず、WasmGCの構造体・配列を使う。文字列もWasmGCの配列で、組み込み操作はprelude（Kekkaiで書いたランタイム）の関数になる
5. **JSグルー生成**：capabilityの宣言（WIT風）から、Workersのバインディングを呼ぶ橋渡しコードを自動生成する

**Workersへの対応づけ**

| Kekkai | Workers |
| --- | --- |
| `DbPool` / `Tx` | D1（アトミックなバッチ実行）。対話的なトランザクションが必要ならDurable Objectsのストレージ |
| ストレージcapability | KV、R2 |
| `Net` | fetch |
| 長時間の処理（RCTパイプラインなど） | Workflows＋Cron Triggers |
| 構造化並行性 | グルー側の `Promise.all`＋`AbortController` |

**設計判断**

- **WASMを選ぶ理由**：i32/i64がネイティブにあり、篩型やオーバーフローの意味論をLeanの仕様と一致させられる（JSは数値がf64のみ）。独立したメモリで動き、外部とはグルーしか通らない構造がcapabilityと一致する。組み込み操作はKekkaiで書いたランタイムのprelude（`lib/prelude`）としてモジュールに含めるので、ホストに求めるのはcapabilityの操作だけになる。コマンドラインのプログラムとコンパイラ自身はWASIのコマンドとしてwasmtimeで動く。
- **非同期の橋渡し**：I/Oに到達する関数はエフェクト型から分かるので、それだけをコンパイラがステートマシン（CPS）に変換する。WorkersでJSPIが使えるようになれば置き換える。
- **境界のコスト**：文字列とバイト列はJSとの間でコピーが発生する。想定する用途では問題にならない規模。

### セルフホスティング

1. WASMにしたコンパイラ（`bootstrap/kek.wasm`）をブートストラップ用にリポジトリへ置く（Zigと同じ方式）
2. **stage1**：bootstrapで `compiler/` をコンパイルする
3. **stage2**：stage1で自分自身をもう一度コンパイルし、両者がビット単位で一致すること（不動点）をCIで確認する

- コンパイラが受け取るcapabilityはファイル読み取り程度なので、コンパイラ自身がhermeticであることを自分の型で保証できる。
- コンパイラがWASMになるので、Playgroundはブラウザ内でコンパイルも実行も完結し、静的サイトとして配信できる。
- Leanの参照インタプリタとの差分テストでコンパイラを検証する。

## 検証戦略

仕様とメタ定理はLeanで書き、コンパイラ実装とは差分テストで突き合わせる。AWS Cedarの verification-guided development と同じ戦略である。

**Leanに書くもの**

- 構文、型付け規則、操作的意味論（中間表現の意味論として定義）
- 型安全性（progress / preservation）
- エフェクト健全性：渡されていないcapabilityの副作用は実行されない
- 線形性：`Tx` は必ず1回だけ消費される
- capabilityの非漏洩
- 実行可能な参照インタプリタ

**差分テスト**

- ランダムに生成したプログラムをLeanの参照インタプリタとコンパイラが出力したWASMの両方で実行し、型検査結果と実行結果を比較する。
- LLMに実装を書かせる場合も、Lean側がテストオラクルになる。

**前提と方針**

- SMTソルバは公理扱いとする。
- 束縛変数はde Bruijnインデックスかlocally namelessで表す（未決）。
- 非干渉性の証明は重いため最後に回す。

## ロードマップ

各段階で「Leanで定理を証明→実装→差分テスト」を一周させてから次へ進む。

1. **最小コア**：関数、第二級capability、エフェクト。型安全性とエフェクト健全性を証明する（Lean数百行規模）。
2. **線形 `Tx`**：線形性の定理、`transaction` ブロック、`Outbox`。ここで実際のDBとつなぐ。あわせて個人情報の最小版（表示不可のPii型）を入れる。
3. **篩型**：SMT連携、添字の安全性、入力検証。
4. **構造化並行性**：`Scope`、キャンセルとデッドライン。ここでHTTPサーバーとして実用最小限になる。
5. **決定性と冪等性**：`Clock`・`Random` のcapability化、`Idempotent` ハンドラ。
6. **インクリメンタル処理**：ハッシュによるコード管理、`action`、`derived`。
7. **認可と情報フロー**：`Can<A, r>`、本格的な情報フロー型（PIIラベル）、テナント分離、非干渉性の証明。
8. **セルフホスティング**：Kekkaiでコンパイラを書き、stage2とstage3の一致を確認する。

## 既存言語との比較

型システムの部品（エフェクト、篩型、capability）を揃えた言語は既に多い。差別化の軸はサーバー固有の保証とインクリメンタル処理に置く。

| 言語 | 重なる点 | 足りない点 |
| --- | --- | --- |
| F\* | 篩型、エフェクト、SMT | サーバー向けではなく重い |
| Ur/Web | 型付きWeb、DBスキーマ型 | 開発がほぼ停止 |
| Effekt | 第二級capabilityによるエフェクト | 篩型、線形性、サーバー機能 |
| Koka | 代数的エフェクト | capability、篩型 |
| Unison | ハッシュによるコード管理 | 証明系 |
| Liquid Haskell | 篩型＋SMT | Haskellの拡張 |
| [Clank](https://github.com/janka102/clank) | AI向け、エフェクト、affine型、篩型、HTTPサーバー | 線形Tx、情報フロー |
| [Edda](https://github.com/edda-lang/edda) | エフェクト行、引数で渡すcapability | サーバー固有の保証 |
| [Logos](https://github.com/shammyali/logos) | 篩型、線形型、capability、参照インタプリタ | サーバー固有の保証 |

**本言語の差分**：tx内のロールバック不能な副作用の禁止、情報フロー型によるPII・テナント分離、言語仕様としてのインクリメンタル処理、WasmGCへの直接出力とセルフホスティング、Leanによる仕様化。AI向け言語群はいずれも若いリポジトリで成熟度は未知数。
