# 並行ビルド（self-hosting 後に着手）

## 1回のビルド内

依存関係は定義単位のグラフ。依存し合わない定義の型検査・SMT証明・コード生成は並列に実行する。

## アクションキャッシュ（実装済み）

Bazel と同じく、コマンドの実行を「入力のダイジェスト → 出力」のアクションとして扱い、`.kek-cache/` に保存する。どのエントリも一時ディレクトリ（ファイル）に書いてからリネームするので、複数の worktree・エージェントが同時に使ってもロックは要らない。キーには必ずコンパイラのステージ（コンパイラ・prelude・core のハッシュ）が入る。

| アクション | キー | 出力 |
| --- | --- | --- |
| ビルド（入力） `build/src-*` | パス・引数・プログラムのファイルの内容 | `module.wasm`・`worker.js`・`kekkai_meta.js`・`wrangler.toml`（出力先になければ）・コンパイラの診断。ヒットするとコンパイラを起動しない |
| ビルド（定義） `build/<stage>/*` | プログラム全体の定義ハッシュ・エントリポイント・ハンドラの引数 | `module.wasm`。コメントや整形だけの変更でもヒットする（型検査だけ行う） |
| テストの一覧 `test-list/*` | プログラムのファイルの内容 | テスト名・`trans` ハッシュ・引数。ヒットするとコンパイラを起動しない |
| テスト結果 `test/<オプション>/*` | テストの `trans` ハッシュ・ケース数（オプション：seed・clock・`-net`/`-db` の内容） | 状態と出力。キャッシュにないテストだけをビルドして実行する |
| ミューテーション `mutate/pairs-<stage>.tsv` | 変異体（関数の `trans`・位置・変異）× テストの `trans` | 結果（追記専用の 1 ファイル） |

ソースが変わらなければコンパイラを一度も起動しないので、コンパイラ自身の `kek build` は 5.7 秒から 0.36 秒、テスト 100 個のプログラムの `kek test` は約 0.6 秒になる。

**影響範囲（affected）**：`kek affected -diff <rev> <path>` は git の revision との差分から、変わった定義、`trans` が変わった（＝振る舞いが変わりうる）定義、走らせるべきテスト、ビルド出力が変わるかを出す（`-json` あり）。`kek test -affected <rev>` はそのテストだけを実行するので、キャッシュのない CI でも変更の影響を受けたテストだけが走る。

**リモートキャッシュ**：`KEK_REMOTE_CACHE=<url>` で、アクションの結果を Bazel のリモートキャッシュと同じ HTTP プロトコル（`GET`/`PUT <url>/ac/<sha256>`）で共有する。bazel-remote（`--disable_http_ac_validation`）や PUT を受け付ける任意のサーバー、`file://` の共有ディレクトリが使える。CI の 1 台目が書いた結果を 2 台目や開発者の手元がそのまま使う。通信できないときはミスとして扱う。

**定義ハッシュ**：`trans` は呼び出しグラフの強連結成分ごとのマークル木で計算する（O(定義 + 呼び出し)）。コンパイラ自身（約 1500 関数）で約 3 秒。

**未実装**：リモート実行（Remote Execution API）。

## コンパイルの速さ（GC・常駐プロセス・定義単位のキャッシュ）

コンパイラ自身（約 2000 関数）を一つのプログラムとしてビルドし、関数本体を 1 か所変えて再ビルドした時間で比べる（`kek build-timings <path>` が段階ごとの時間を出す）。

| 構成 | 再ビルド |
| --- | --- |
| 以前（wasmtime 既定の GC、型検査 2 回） | 約 4.7 秒（ばらつきが大きく、10 秒を超えることもある） |
| コピー GC | 約 1.8 秒 |
| コピー GC + 常駐プロセス（`kek daemon`） | 約 1.3 秒 |

- **GC**：wasmtime の既定のコレクタ（遅延参照カウント）は、コンパイラのように短命なオブジェクトを大量に作る処理で非常に遅い。`kek` はコンパイラもプログラムもコピー GC（`-C collector=copying`）で動かし、コンパイラには大きな初期ヒープ（予約だけで、小さなプログラムのメモリは増えない）を与える。コンパイラ自身のビルドは約 10 秒から約 1.3 秒になり、テストのプログラムも 2 倍以上速い。
- **常駐プロセス**（`kek daemon start`）：コンパイラを起動したままにし（`serve`、`compiler/serve.kek`）、ソースファイルごとの構文木と core ライブラリの構文木をメモリに残す。ビルドは変わったファイルだけを構文解析し、プロセスの起動もない。起動していれば `./kek` が自動で使い、使用中なら自分でコンパイラを動かす（並列の実行を直列にしない）。
- **定義単位のディスクキャッシュは採用しなかった**：関数ごとの lower の結果（IR）を、型の番号付けやクロージャの順序を再現できる形（記号化した IR と共有状態への効果の列）でディスクに保存し、再生する方式を実装して、出力がフルビルドとバイト単位で一致することまで確かめた。しかしコンパイラ規模で、pack（約 5MB）の読み込みと再生に 1.2 秒かかり、lower し直す（0.56 秒、コピー GC では約 0.2 秒）より遅かった。構文解析と型検査の結果も同じで、Kekkai でディスクから復元するほうが計算し直すより重い。したがって再利用はメモリ上（常駐プロセス）で行う。
- 残りの時間（常駐プロセスで約 1.3 秒）は型検査・lower・コード生成がそれぞれ約 0.2〜0.3 秒。定義単位で型検査を省いても 0.3 秒程度しか減らないため、今は行っていない。

## 複数エージェントの同時ビルド

- キャッシュのキーは「定義ハッシュ＋依存＋コンパイラのバージョン」。同じキーなら結果も同一なので、書き込みにロックは不要（アトミックなリネームのみ）。
- 共有の出力ディレクトリは持たない。成果物はハッシュで管理し、各ワークスペースは「現在の版のハッシュ」を指すだけにする。複数のgit worktreeが1つのキャッシュを同時に共有できる。
- kek の常駐プロセスは複数ワークスペースからの要求を同時に受け付ける。各要求は「ソースのスナップショットに対する純粋関数」として処理する。

## テストの並列実行

DB・ポート・ファイルはcapabilityなので、テストごとに独立したモックを渡せば並列実行で干渉しないことが型から分かる。本物の共有リソースを受け取るテストだけをスケジューラが直列に実行する。

現在の `kek test` はすべての capability をモックにするので、テストを `-j n`（既定は CPU 数）個の wasmtime プロセスに分けて並列に実行し、結果は宣言順に表示する。1 つのプロセスが多数のテストを順に実行し（`--batch`、テストごとにモックと乱数を初期化する）、テストがトラップしたときだけ残りを新しいプロセスでやり直す。

## エージェント間のコード競合

定義単位でマージする。同じ補助関数の重複作成は `kek similar`（実装済み。`-diff <rev>` で PR が追加・変更した定義だけを検査）で検出する。

## kek 常駐プロセスの検証

- セルフホスティング後、常駐プロセスはKekkaiで書かれたサーバーになる。エージェントによる並行利用がそのままランタイムの負荷試験になる。
- 判定基準：ビルドは純粋関数なので、どんな並行スケジュールでも直列実行と同じハッシュになるはず。これを並行処理バグの検出に使う。
- 決定的シミュレーションテスト：Clock・Random・I/Oをシミュレーション用のcapabilityに差し替え、仮想エージェントを大量に走らせる。遅延や実行順序をランダムに変え、バグはシード値で完全に再現する。
- 実行環境：常駐プロセスは手元のwasmtime（WASI 0.3）上で動かす。1インスタンス内でスレッド並列はできないので、複数インスタンスが同じディスク上のキャッシュを共有する構成にする。これはロック不要なキャッシュ設計の試験にもなる。
