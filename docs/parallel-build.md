# 並行ビルド（self-hosting 後に着手）

## 1回のビルド内

依存関係は定義単位のグラフ。依存し合わない定義の型検査・SMT証明・コード生成は並列に実行する。

## 複数エージェントの同時ビルド

- キャッシュのキーは「定義ハッシュ＋依存＋コンパイラのバージョン」。同じキーなら結果も同一なので、書き込みにロックは不要（アトミックなリネームのみ）。
- 共有の出力ディレクトリは持たない。成果物はハッシュで管理し、各ワークスペースは「現在の版のハッシュ」を指すだけにする。複数のgit worktreeが1つのキャッシュを同時に共有できる。
- kek の常駐プロセスは複数ワークスペースからの要求を同時に受け付ける。各要求は「ソースのスナップショットに対する純粋関数」として処理する。

## テストの並列実行

DB・ポート・ファイルはcapabilityなので、テストごとに独立したモックを渡せば並列実行で干渉しないことが型から分かる。本物の共有リソースを受け取るテストだけをスケジューラが直列に実行する。

## エージェント間のコード競合

定義単位でマージする。同じ補助関数の重複作成は `kek similar` で検出する。

## kek 常駐プロセスの検証

- セルフホスティング後、常駐プロセスはKekkaiで書かれたサーバーになる。エージェントによる並行利用がそのままランタイムの負荷試験になる。
- 判定基準：ビルドは純粋関数なので、どんな並行スケジュールでも直列実行と同じハッシュになるはず。これを並行処理バグの検出に使う。
- 決定的シミュレーションテスト：Clock・Random・I/Oをシミュレーション用のcapabilityに差し替え、仮想エージェントを大量に走らせる。遅延や実行順序をランダムに変え、バグはシード値で完全に再現する。
- 実行環境：常駐プロセスは手元のwasmtime（WASI 0.3）上で動かす。1インスタンス内でスレッド並列はできないので、複数インスタンスが同じディスク上のキャッシュを共有する構成にする。これはロック不要なキャッシュ設計の試験にもなる。
